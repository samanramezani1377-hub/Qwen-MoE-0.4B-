# بودجهٔ معماری: کل مدل حدود ۲B

وضعیت: طرح اولیه؛ مدل هنوز پیاده‌سازی، آموزش یا بنچمارک نشده است.

## هدف
- کل مدل نهایی: حدود ۲ میلیارد پارامتر یکتا؛ هدف قدیمی ۰٫۴B پارامتر کل لغو شده است.
- مدل متن‌محور، فارسی‌فهم، استدلال‌محور و قابل اجرای آفلاین روی اندروید.
- مدل مرجع: `Qwen/Qwen3.5-2B`.
- فقط منابع رایگان؛ هیچ GPU یا سرویس پولی بدون تأیید اجرا نمی‌شود.

## ممیزی بازتولیدپذیر

اسکریپت `scripts/audit_model.py` و Notebook `notebooks/01_model_audit.ipynb` اکنون revision حل‌شدهٔ Hugging Face را با SHA ثبت می‌کنند، config و tokenizer metadata را می‌خوانند و تعداد پارامترهای اعلام‌شده از طرف Hub را در صورت وجود گزارش می‌کنند. وزن‌های safetensors دانلود نمی‌شوند. اگر Hub پارامترها را در metadata ارائه نکند، گزارش صریحاً این محدودیت را نشان می‌دهد؛ اندازهٔ فایل به‌تنهایی معادل شمارش دقیق پارامترها نیست.

گام بعدی ممیزی دقیق وزن‌ها، خواندن header/shapeهای safetensors یا استفاده از فایل index است. این مرحله باید قبل از انتخاب نهایی اندازهٔ متخصص‌ها انجام شود.

## شمارش پارامتر فعال

در config مرجع `vocab_size=248320` و `hidden_size=2048` است؛ پس `248320 × 2048 = 508559360` پارامتر برای ماتریس embedding. اگر embedding و LM head مشترک باشند، وزن‌ها در تعداد کل یکتا یک بار شمرده می‌شوند؛ اما LM head متراکم برای logits کل واژگان از همهٔ این وزن‌ها استفاده می‌کند. بنابراین 508.6M اندازهٔ embedding است، نه کل پارامتر فعال all-in. با attention و FFN، عدد فعال کل از آن بیشتر است.

گزارش باید جدا کند: (۱) کل پارامترهای یکتا، هدف ≈2B؛ (۲) فعال‌های بدنهٔ Transformer/MoE؛ (۳) هزینهٔ LM head/logits و جمع all-in. اگر سقف 508.6M برای کل مسیر تولید شامل logits باشد، با خروجی متراکم استاندارد و hidden=2048 شدنی نیست.

## طرح پایه

| مؤلفه | مقدار |
|---|---:|
| لایه‌ها | 24 |
| hidden size | 2048 |
| واژگان | 248320، باید با tokenizer تثبیت شود |
| attention | حفظ ترتیب واقعی linear/full از config |
| متخصص‌ها در هر FFN تبدیل‌شده | 8 |
| top-k | 2 |
| expert intermediate | 768، نقطهٔ شروع آزمایشی |
| کوانتیزه‌سازی | آزمایش INT4 و مقایسه با INT8 |

## بودجهٔ FFN

برای SwiGLU سه‌ماتریسی بدون bias: `P_expert = 3 × hidden × expert_intermediate`.

- هر متخصص در هر لایه: `3 × 2048 × 768 = 4,718,592` پارامتر.
- همهٔ 8 متخصص در 24 لایه: حدود 906M پارامتر.
- دو متخصص فعال در هر لایه: حدود 226.5M پارامتر فعال FFN.
- Router خطی سادهٔ 2048×8 در 24 لایه: حدود 393,216 پارامتر، بدون bias.

این‌ها فقط برآورد فرمولی FFN و Router هستند؛ attention، embedding/head، normها و سایر اجزا را شامل نمی‌شوند. همچنین فرض تبدیل FFN در تمام 24 لایه است و هنوز با معماری/وزن‌های واقعی سازگار نشده. اندازهٔ متخصص‌ها بعد از شمارش checkpoint واقعی تنظیم می‌شود تا کل مدل نزدیک 2B بماند.

## حافظهٔ خام نظری برای 2B وزن
- FP16/BF16: حدود 4GB
- INT8: حدود 2GB
- INT4: حدود 1GB

سربار quantization، runtime، activations، cache و سیستم‌عامل در این اعداد نیست. اجرای موبایل باید روی گوشی واقعی از نظر RAM و سرعت آزمایش شود؛ MoE با فعال‌کردن چند متخصص، وزن‌های ذخیره‌شده را خودکار کوچک نمی‌کند.

## مراحل بعدی
1. اجرای ممیزی متادیتا و ثبت SHA دقیق config/tokenizer.
2. شمارش دقیق پارامترهای checkpoint از tensor shapes و تفکیک اجزای متن/چندوجهی.
3. اصلاح طرح FFN-MoE براساس بودجهٔ واقعی پارامترها، نه تخمین به‌تنهایی.
4. ساخت نمونهٔ محدود با یک FFN-MoE و تست forward/backward.
5. ثبت جداگانهٔ کل پارامترها، فعال‌های بدنه و هزینهٔ logits.
6. بررسی runtime اندروید و سپس آموزش Router و تقطیر دانش با ابزار رایگان.
