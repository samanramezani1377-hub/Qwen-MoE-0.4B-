# بودجهٔ معماری پیشنهادی: حدود ۵۰۸ میلیون پارامتر فعال

تاریخ: 2026-10-25  
وضعیت: طرح محاسباتی اولیه؛ هنوز پیاده‌سازی، آموزش یا بنچمارک نشده است.

## هدف تثبیت‌شده

- مدل متن‌محور و فارسی‌فهم برای اجرای آفلاین روی اندروید با CPU و حافظهٔ محدود.
- هدف محاسباتی: حدود 508.6M پارامتر فعال در هر توکن؛ تعداد پارامترهای کل می‌تواند بیشتر باشد.
- معلم/مرجع: `Qwen/Qwen3.5-2B`.
- منابع رایگان؛ هیچ GPU یا سرویس پولی بدون اجازهٔ صریح اجرا نمی‌شود.
- این هدف جایگزین تفسیر قبلی «حداکثر 0.4B پارامتر کل» است. نام مخزن `Qwen-MoE-0.4B` فعلاً تاریخی است و اندازهٔ واقعی هدف را نشان نمی‌دهد.

## نکتهٔ شمارش بسیار مهم

در config مرجع، vocab=248,320 و hidden_size=2,048 است؛ بنابراین جدول embedding مشترک مرجع برابر است با:

`248,320 × 2,048 = 508,559,360`

این عدد به‌خودی‌خود تعداد پارامتر فعال نیست. در مدل مقصد با hidden_size=1,024 و همان واژگان، ماتریس embedding/خروجی مشترک برابر است با:

`248,320 × 1,024 = 254,279,680`

در زمان تولید توکن، projection خروجی برای محاسبهٔ logits روی کل واژگان از این ماتریس استفاده می‌کند؛ بنابراین در شمارش عملیاتیِ این سند، تمام 254.28M وزن خروجی جزو پارامترهای فعال هر توکن شمرده می‌شوند. ورودی embedding فقط ردیف توکن ورودی را lookup می‌کند. چون وزن‌ها tied هستند، جدول در تعداد پارامترهای یکتای کل مدل فقط یک بار شمرده می‌شود.

## معماری هدف پیشنهادی

| مؤلفه | مقدار |
|---|---:|
| نوع | متن‌محور، decoder-only، MoE |
| لایه‌ها | 24 |
| hidden size | 1,024 |
| واژگان | 248,320؛ توکنایزر مرجع باید بررسی شود |
| embedding / LM head | مشترک (tied) |
| الگوی attention | 18 لایه linear attention + 6 لایه full attention (نسبت 3:1) |
| linear attention | 8 سر Q/K و 8 سر V، بُعد هر سر 64؛ ابعاد دقیق باید با پیاده‌سازی سازگار شوند |
| full attention | 16 سر Q، 4 سر KV، بُعد سر 64 |
| FFN | SwiGLU با 8 متخصص در هر لایه |
| top-k | 2 متخصص فعال در هر توکن در هر لایه |
| expert intermediate size | 1,280 |
| vision tower | حذف؛ هدف این پروژه فقط متن است |
| quantization هدف اجرا | آزمایش INT4؛ مقایسه با INT8 در صورت امکان |

این پیکربندی یک طراحی کوچک‌شدهٔ الهام‌گرفته از backbone ترکیبی Qwen3.5 است، نه یک config آماده که مستقیماً checkpoint اصلی را بارگذاری کند. ابعاد سرها، RoPE، لایه‌های linear attention و runtime اندروید باید در یک نمونهٔ کوچک اعتبارسنجی شوند.

## محاسبهٔ FFN متخصص‌ها

برای یک FFN از نوع SwiGLU، با فرض سه ماتریس بدون bias:

`P_expert = 3 × hidden × expert_intermediate`

پس:

- هر متخصص در هر لایه: `3 × 1,024 × 1,280 = 3,932,160` پارامتر.
- کل وزن متخصص‌ها: `3,932,160 × 8 × 24 = 754,974,720` ≈ 754.97M.
- وزن FFN متخصص‌های فعال در هر توکن: `3,932,160 × 2 × 24 = 188,743,680` ≈ 188.74M.

Router با یک ماتریس خطی 1,024×8 برای هر لایه، بدون bias، حدود `1,024 × 8 × 24 = 196,608` پارامتر دارد.

## بودجهٔ فعال در هر توکن (برآورد)

| بخش فعال | پارامترها، تقریباً |
|---|---:|
| LM head روی کل واژگان، tied با embedding | 254.280M |
| دو متخصص FFN در هر یک از 24 لایه | 188.744M |
| 18 لایهٔ linear attention، شامل projectionها و برآورد کوچک convolution | 47.59M |
| 6 لایهٔ full attention | 15.73M |
| Routerها | 0.197M |
| normها و اجزای کوچک | حدود 0.05M |
| **جمع فعال تخمینی** | **حدود 506.6M** |

این مقدار حدود 0.4% پایین‌تر از هدف 508.6M است؛ برای اجرای موبایل، expert intermediate=1,280 (مضرب مناسب برای kernelهای رایج) از تنظیم غیرمعمولی مثل 1,296 ترجیح داده شده است. مقدار 506.6M «برآورد معماری» است و پس از پیاده‌سازی باید با شمارش واقعی پارامترها و مسیر forward اصلاح شود.

## تعداد کل پارامترهای یکتا (برآورد)

| بخش | پارامترها، تقریباً |
|---|---:|
| embedding/LM head مشترک | 254.280M |
| همهٔ 8 متخصص در 24 لایه | 754.975M |
| تمام attentionها | 63.32M |
| Routerها | 0.197M |
| normها و اجزای کوچک | حدود 0.16M |
| **جمع کل یکتا** | **حدود 1.073B** |

به‌دلیل tied بودن embedding/LM head، ماتریس 254.28M فقط یک بار در تعداد کل یکتا حساب شده است. اگر head جداگانه باشد، حدود 254.28M پارامتر دیگر اضافه می‌شود.

## حافظه و هزینهٔ موبایل

برآورد صرفاً برای وزن‌های 1.073B پارامتری، بدون سربار quantization/runtime/cache:

| دقت | اندازهٔ تقریبی وزن‌ها |
|---|---:|
| FP16/BF16 | 2.15 GB (حدود 2.00 GiB) |
| INT8 | 1.07 GB (حدود 1.00 GiB) |
| INT4 | 0.54 GB (حدود 0.50 GiB) |

در عمل INT4 نیاز به حافظهٔ بیشتر برای scale/metadata، runtime، activations و cache دارد. در هر توکن تقریباً 506.6M وزن فعال خوانده/استفاده می‌شود؛ در حد نظری INT4 این معادل حدود 253 MB وزن‌های فعال برای هر توکن است، بنابراین سرعت به پهنای باند حافظه و kernelهای کم‌دقت بسیار وابسته خواهد بود. «۵۰۸M فعال» به‌معنی سریع بودن روی گوشی نیست.

## انتقال وزن و تقطیر

به‌دلیل تغییر hidden size از 2,048 به 1,024 و تغییر ابعاد attention، وزن‌های Qwen3.5-2B را نمی‌توان بدون تبدیل به همهٔ لایه‌های مقصد کپی کرد. embedding/head نیز تغییر ابعاد دارد. مسیر واقع‌بینانه:

1. تثبیت revision دقیق config/tokenizer و ممیزی نسخهٔ Transformers.
2. ساخت config مقصد و تست forward با وزن‌های تصادفی روی یک نمونهٔ کوچک.
3. بررسی runtime CPU/Android و پشتیبانی از hybrid linear attention و MoE.
4. آزمایش projection/فشرده‌سازی embedding و انتقال جزئی وزن‌ها، سپس distillation از معلم.
5. ارزیابی فارسی، منطق، ریاضی، پیروی از دستور، اندازهٔ فایل، RAM و سرعت روی سخت‌افزار هدف.
6. تنها پس از نتیجهٔ آزمایش کوچک، تصمیم دربارهٔ توسعهٔ کامل مدل.

هیچ‌یک از این مراحلِ پیاده‌سازی، آموزش یا بنچمارک هنوز انجام نشده است.
